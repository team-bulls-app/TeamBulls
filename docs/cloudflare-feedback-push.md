# Notificações de feedback com Cloudflare Free

Este caminho usa um Worker agendado a cada minuto em vez de Firebase Cloud Functions. O projeto Firebase pode continuar no Spark. O FCM continua sendo o serviço que entrega avisos à barra do celular, e é um produto sem custo. O Worker lê novos documentos `feedback`, verifica o vínculo atual `users/{studentId}.trainerId`, consulta apenas os aparelhos daquele aluno e envia somente `feedbackId` e categoria. O texto do feedback nunca entra no push. O app continua exigindo permissão de notificação; iPhone exige o app instalado na Tela de Início. Som e visibilidade dependem das configurações do aparelho.

**Estado:** o código e os testes podem ser revisados antes da publicação. Só haverá avisos com o app fechado depois de configurar Cloudflare, a chave pública Web Push e fazer um teste real em um celular. Não configure a função `notifyNewFeedback` do Firebase ao mesmo tempo, para evitar avisos duplicados.

## Preparação e publicação

1. Crie uma conta gratuita em [Cloudflare](https://dash.cloudflare.com/sign-up). Em Workers & Pages, prepare o subdomínio gratuito `workers.dev`. Não é necessário domínio próprio. Confirme que o plano selecionado é Workers Free antes de publicar.
2. No projeto Google `teamms-app`, crie uma **conta de serviço dedicada** para avisos. Dê somente os papéis `roles/datastore.viewer` (leitura Firestore) e `roles/firebasecloudmessaging.admin` (envio FCM HTTP v1). Não use conta Owner/Editor nem a chave administrativa geral do Firebase. O primeiro papel ainda permite leitura de outras coleções; por isso a chave deve existir exclusivamente como segredo do Worker e ser rotacionada se houver exposição.
3. Gere **uma chave JSON** dessa conta de serviço, se a política de sua organização permitir. Não a copie para GitHub, não a cole em uma conversa e não a salve na pasta do app. Se a criação de chave estiver bloqueada, não reduza a proteção do projeto apenas para contornar a política; revise um método de autenticação sem chave.
4. Em Firebase Console → Configurações do projeto → Cloud Messaging → Certificados push da Web, gere ou use um par Web Push. Copie apenas a **chave pública** para `webPushVapidKey` em `config_v10_7.js`. A chave privada permanece no Firebase. Publique essa pequena alteração com os quatro gates verdes. Os alunos devem abrir a versão nova e tocar em “Ativar notificações” no celular.
5. Na pasta `cloudflare-feedback-push`, crie um banco D1 gratuito com o nome `team-bulls-feedback-push` e preencha o `database_id` em `wrangler.toml`. Aplique `migrations/0001_init.sql` **antes** de publicar o Worker. Ela grava o instante inicial para não reenviar feedbacks antigos. Os feedbacks criados entre a migração e a publicação serão processados depois.
6. Cadastre o JSON da conta de serviço em **Workers → Settings → Variables and Secrets** com o nome `SERVICE_ACCOUNT_JSON`, como **Secret**. O valor completo é o JSON, incluindo `private_key`. Não use variável pública. Publique o Worker com o agendamento `* * * * *` de `wrangler.toml`. A URL pública do Worker sempre responde 404; não há endpoint que aceite pedidos de envio.
7. Envie um feedback de teste para um aluno ativo usando uma das cinco categorias. Confirme no D1 que o item passa de `pending` para `done`, e confira o aviso em um Android com o app fechado. Teste também em iPhone instalado na Tela de Início. Um aluno de outro treinador ou com vínculo encerrado não deve receber o aviso.

Para executar por terminal, o fluxo é `npx wrangler@4 d1 create team-bulls-feedback-push`, depois `npx wrangler@4 d1 migrations apply team-bulls-feedback-push --remote`, `npx wrangler@4 secret put SERVICE_ACCOUNT_JSON` e `npx wrangler@4 deploy`, sempre a partir de `cloudflare-feedback-push` e após revisar a conta/projeto de destino. O comando de secret pede o valor de maneira privada; não coloque a chave como argumento de linha de comando. Teste local: `node scripts/cloudflare-feedback-push-check.mjs` na raiz do repositório.

## Operação, limites e segurança

- O Worker tenta novamente falhas transitórias e registra quais aparelhos já receberam cada feedback, para evitar repetição em retries. Uma falha entre o envio ao FCM e o registro em D1 ainda pode causar aviso repetido; entrega exatamente uma vez não é garantida pelo FCM.
- O cursor de leitura e a fila de envios são mantidos em D1. O cursor só avança junto com a inserção dos feedbacks na fila. O sistema não apaga nem modifica `feedback`, `users` ou `pushDevices` no Firestore; Rules 28 e App Check do cliente continuam iguais.
- O código limita cada rodada a 20 feedbacks novos, 2 feedbacks para entrega e 15 aparelhos por página. Se houver acúmulo, ele escoa nas rodadas seguintes. Monitore erros de Cron e crescimento de `feedback_outbox`; indisponibilidade do Worker deixa avisos pendentes, sem impedir que o feedback apareça normalmente no app.
- Workers Free tem limites, incluindo 100 mil invocações por dia, 50 subrequisições externas por invocação e tempo de CPU curto. D1 Free também tem cotas. O agendamento de um minuto usa cerca de 1.440 invocações/dia; verifique o uso no painel Cloudflare. Quando um limite gratuito é excedido, as chamadas falham em vez de mudar automaticamente para o plano pago. O Firestore Spark também tem cotas próprias de leitura.
- A conta de serviço tem leitura de Firestore acima das regras de cliente. Nunca exponha seu JSON no app, GitHub, logs, suporte ou chat. Se a chave vazar, revogue-a no Google Cloud e cadastre uma nova no segredo do Worker.
